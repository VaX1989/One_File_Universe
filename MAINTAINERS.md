## Target structure

As the community grows, maintainership should be delegated by area rather than accumulating global repository access. Target areas include core identity, time/history, runtime, build/composition, rendering, astronomy, planetology, surface, life, civilization, individuals, matter, gameplay, product/UX, accessibility, audio, persistence, science review, security, and community operations.

The machine-readable area catalog is `config/governance/areas.json`.

## Maintainer responsibilities

Maintainers are expected to review within scope, preserve the Constitution and authority contracts, keep tests and documentation healthy, classify uncertainty honestly, mentor new contributors, and avoid becoming throughput bottlenecks.

Maintainers must not approve scientific truth merely because a model is visually convincing, approve architectural authority merely because code exists, or claim tests/platforms that did not execute.

## Becoming a maintainer

See `docs/community/MAINTAINER_LADDER.md`. The important signal is not number of commits; it is repeated evidence that a contributor improves both the code and the reliability of the project around them.
